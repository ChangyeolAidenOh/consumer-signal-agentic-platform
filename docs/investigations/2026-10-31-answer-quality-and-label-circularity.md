## 0. 요약

Streamlit 화면으로 에이전트에 직접 질문을 던지는 10분 사이에, 평가셋 89문항과 라우팅 정확도 83.1%로는 보이지 않던 답변 수준의 문제 네 가지가 드러났다. 원인을 추적하는 과정에서 초기 가설 하나(문서 앞부분만 보고 있다)는 데이터로 기각되었고, 대신 두 가지 사실이 새로 확인되었다.

1. VoC 데이터는 후기 원문이 아니라 검색 결과 발췌문(중앙값 약 140자)이다.
2. 상위 파이프라인의 이탈 신호 탐지기가 경쟁사 브랜드명 자체를 이탈 키워드로 사용하고 있어, 대표 발견으로 제시해 온 "경쟁사 언급 문서 이탈률 82.2% vs 20.4%"가 상당 부분 정의에서 나온 숫자다. 브랜드명을 제외하면 이탈 신호 출현율은 38.6% vs 30.9%로 줄고, 표본 크기(101건)에서 통계적으로 유의하지 않다(p≈0.1).

| 지표 | 경쟁사 언급 (n=101) | 비언급 (n=1,643) |
|---|---|---|
| 이탈로 분류된 비율 (라벨 기준) | 82.2% (83) | 20.4% (335) |
| 그중 브랜드명 외 이탈 근거가 없는 문서 | 44 (Active Switcher 83건의 53%) | 0 |
| 브랜드명 제외, 이탈 신호가 하나라도 있는 비율 | 38.6% (39) | 30.9% (507) |

결정: 데이터 재분석(A)에 앞서, 이 숫자에 기반한 주장을 README·포트폴리오·평가셋에서 먼저 바로잡고(B), 재분석은 계획된 작업으로 남긴다.

## 2. 1차 원인 추정

### 2.1 표본으로 전체를 단정 (현상 1)

- Reporter에 들어가는 문맥은 `=== VoC Documents ===` 아래 5건뿐이며, 이것이 1,744건 중 유사도 상위 5건이라는 정보가 없다. 모델 입장에서는 받은 문맥이 세계의 전부다.
- 할루시네이션을 막기 위해 넣은 규칙 "Answer based ONLY on the provided data"가 닫힌 세계 가정으로 작동했다. 지어내는 오류는 줄였지만, 없는 것을 없다고 단정하는 오류로 옮겨갔다.
- 벡터 검색은 질문과 의미가 비슷한 문서를 찾을 뿐, "두 브랜드를 모두 언급"이라는 논리 조건을 걸지 못한다. 메타데이터 필터(`competitor_mentioned`)가 존재하지만 Retriever는 사용하지 않는다.
- "데이터에 X가 있는가"의 정답은 SQL 개수 조회인데, 에이전트는 미리 정의된 쿼리만 사용할 수 있어 이 질문에 맞는 도구가 없다.

### 2.2 기억의 착시 (현상 2)

- API 요청 스키마는 `query` 하나이고, 에이전트 상태에 대화 기록 필드가 없으며, 그래프는 매번 새로 실행된다. Streamlit은 기록을 화면에만 쌓고 API로 보내지 않는다.
- "1번과 2번"이 맞게 나온 것은 같은 SQL이 같은 정렬(전환 확률 내림차순)로 두 번 실행되어, 직전 답변의 번호 순서와 표의 행 순서가 우연히 일치했기 때문이다.
- 기록을 Reporter에 넘기는 것만으로는 해결되지 않는다. 라우터와 검색이 최신 발화 하나로 동작하므로, 후속 질문을 독립 질문으로 다시 쓰는 단계가 라우팅 앞에 필요하다.

### 2.3 유도 질문 동조 (현상 3)

- 모델의 일반적인 동조 경향에 더해, 프롬프트에 "질문의 전제를 검증하라"는 지시가 없다.
- 구조적으로, 질문이 경로를 정하고 경로가 증거를 정한다. "전문가 마케팅"을 가리키는 질문은 의료 프레임 대응 전략만 불러오고, 반대 근거가 될 다른 층의 데이터는 문맥에 들어오지 않는다. 검색 자체가 확증 편향을 만든다.
- "3~5문장으로 간결하게"라는 지시는 단서를 붙일 자리를 줄여 단정적인 어조를 부추긴다. 정보 질문과 확인 질문을 구분하지 않는다.
- 현상 4e(소멸한 제품 라인 강화 권고)는 같은 원인의 더 심각한 결과다. 세그먼트 경로는 트렌드 데이터를 보지 못한다. 원본 분석의 가치는 세 층을 교차해 읽는 데 있는데, 에이전트는 대부분의 질문을 한 층에서 답한다.

### 2.4 그 외 (현상 4a–4d)

- 4a: Reporter 출력 형식과 화면 렌더링 사이에 약속이 없다. Llama는 평문으로 답해 드러나지 않았고, Claude로 바꾸면서 마크다운 제목이 생겼다. 모델 교체는 정확도뿐 아니라 출력 형식도 바꾼다.
- 4b: 데이터의 브랜드 표기가 세 가지(한글 컬럼명 `안티트로샴푸`, VoC 한국어 원문, 세그먼트 대응 전략의 영어 `Antitro`)로 섞여 있고 기준 사전이 없다.
- 4c: 로컬 CLI 편의를 위해 둔 지연 로딩이, 시작 시 인덱싱을 제거한 뒤 첫 VoC 질문의 비용으로 옮겨갔다. 응답 시간 목표가 정의된 적이 없다.
- 4d: 키워드 목록이 평가셋 문구에 맞춰 다듬어졌고, 평가셋은 작성자가 쓴 질문에 술어까지 통일한 것이라 실사용 문구와 분포가 다르다. 키워드에 걸리지 않으면 LLM 판단으로 넘어가는데, 그 판단을 배포 환경에서는 Claude가 하며, 83.1%는 Llama로 측정한 값이다.

## 3. 딥다이브

### 3.1 기술 관점

초기 추정 외에 두 가지 가설을 추가로 세웠다.

- 가설 T1: Reporter가 각 문서의 첫 300자만 받는다(`preview = doc[:300]`). 블로그 후기가 수천 자라면 비교 내용이 있어도 모델은 볼 수 없다.
- 가설 T2: 임베딩 모델(`jhgan/ko-sroberta-multitask`)의 입력 한도가 128토큰이라, 긴 문서의 벡터는 도입부 의미만 담는다. 검색이 사실상 "제목과 도입부가 질문과 비슷한 문서"를 찾는다.

두 가설은 4월 계획에서 미뤄둔 결정(500자 청킹 여부를 길이 분포 확인 후 결정)과 연결되었고, 그 확인은 수행되지 않았었다. 두 가설 모두 4절에서 검증했다.

### 3.2 기획·작업 관점

- 완료의 기준이 "배포되고 경로가 맞는다"였지 "답이 맞는다"가 아니었다. 4월 작업의 대부분은 배포 디버깅이었고, 답변 내용 검증은 계속 뒤로 밀렸다.
- 측정하기 쉬운 것(라우팅)을 측정했고, 그 숫자를 품질처럼 다뤘다. 89문항에 정답과 채점 기준이 적혀 있었지만 답변은 채점하지 않았다.
- 라우터 정확도 62% → 83.1% 과정에서 18개 문항의 정답 라벨을 라우터 결과를 본 뒤 수정했다. methodology 카테고리 신설로 인한 수정은 정당했으나, 일부는 "라우터가 보낸 곳도 합리적"이라는 이유로 라벨을 결과에 맞춘 것이다. 결과를 보고 정답을 바꾸면 점수는 오르지만 측정의 의미는 약해진다.
- 바꾼 뒤 다시 재지 않았다. Llama → Claude, 단발 API → 채팅 화면으로 바뀔 때 평가를 다시 돌리지 않았다.
- 채팅 화면이라는 형태가 "이어서 물어도 된다"는 약속을 했고, 백엔드는 그 약속을 지킬 수 없었다. 화면을 제안할 때 백엔드 계약과의 차이를 짚지 않았다.
- 화면 테스트 확인 목록이 기계적 동작(상태 표시, 배지, 캐시, 남은 횟수)만 담았다. 실제 사용자처럼 이어서 묻고 되묻는 시나리오는 없었다. 만든 사람이 아는 질문으로 하는 테스트는 이런 문제를 보여주지 않는다.
- 스크린샷 후보로 "직접 비교 후기가 없다"는 답변을 할루시네이션 방지 사례로 추천했으나, 정답과 대조하지 않은 판단이었다. 이후 철회했다.
- 미뤄둔 결정(청킹, 답변 채점, 충돌 해결 원칙의 프롬프트 반영)이 추적되지 않았다.

### 3.3 운영 관점

- 비용 상한(`max-instances=1`)이 시작 시 인덱싱이라는 잠재 결함을 드러냈듯(10-26 기록), 이번에는 실사용이 평가 체계의 결함을 드러냈다. 운영 환경의 제약과 실제 사용은 테스트 환경이 가려 온 문제를 노출한다.
- 모델 교체(Llama → Claude)가 라우팅 판단 주체, 출력 형식, 어조를 동시에 바꿨지만 배포 환경에서의 재측정은 없었다. 배포 환경의 라우팅 정확도는 현재 측정되지 않은 상태다.
- 비용 측면: 평가셋 89문항을 Claude로 재실행하면 대략 수백 원 수준으로 추정되며, 실행 여부는 별도 승인 사항으로 남겼다.

## 4. 가설 검증

로컬 PostgreSQL(상위 파이프라인 출력 적재본)과 임베딩 모델로 세 가지를 확인했다.

### 4.1 임베딩 입력 한도

```
SentenceTransformer('jhgan/ko-sroberta-multitask').max_seq_length → 128
```

가설 T2의 전제(128토큰)는 사실이다.

### 4.2 문서 길이 분포

| source | n | 길이 중앙값(자) | 최대(자) |
|---|---|---|---|
| blog | 531 | 139 | 170 |
| cafearticle | 589 | 136 | 188 |
| youtube | 624 | 72.5 | 959 |

**가설 T1, T2는 기각.** 블로그와 카페 문서는 대부분 150자 안팎으로, 300자 미리보기에 잘리지 않고 128토큰 한도에도 대체로 들어간다. "문서 앞부분만 보고 있어서 비교 내용을 놓쳤다"는 설명은 틀렸다. 확인 없이 고쳤다면 청킹과 300자 해제라는 효과 없는 작업에 시간을 썼을 것이다.

대신 새로운 사실이 드러났다. **VoC는 후기 원문이 아니라 검색 API가 돌려주는 결과 발췌문이다.** 1,744건은 "후기 1,744편"이 아니라 "후기 발췌 1,744개"다. 비교처럼 문맥이 긴 내용은 어떤 검색 방식으로도 발췌문 안에서 찾기 어렵다. 이는 에이전트가 아니라 데이터 수집 단계의 한계다. 또한 4월에 미뤄둔 청킹 결정은 결과적으로 불필요한 작업이었다(문서가 청크 크기보다 짧다).

### 4.3 두 브랜드 동시 언급 문서 수

```sql
SELECT COUNT(*) FROM voc_documents
WHERE raw_text LIKE '%안티트로%'
  AND (raw_text LIKE '%헤드앤숄더%' OR raw_text LIKE '%헤숄%');
→ 2
```

에이전트의 "직접 비교 후기가 없다"는 답은 결과적으로 거의 맞았다. 그러나 에이전트는 5건만 보고 그렇게 말했으므로, 동시 언급이 200건이었어도 같은 답을 했을 것이다. 추론 과정이 틀렸는데 결과가 우연히 맞은 경우이며, 근거 있는 답으로 볼 수 없다. "카페, 유튜브 중심 수집"이라는 답은 실제 분포(531 / 589 / 624)와 달라 명백히 틀렸다.

## 5. 추가 발견: 라벨 순환

### 5.1 동시 언급 2건의 내용

두 문서 모두 같은 틀의 문장으로 시작한다.

> "안티트로 샴푸 두피 고민 끝낼 수 있을까요 솔직 사용 후기 많은 분들이 안티트로 샴푸 하면 떠올리는 브랜드가 있죠 바로 헤드앤숄더인데요 ..."

"안티트로 샴푸 하면 떠오르는 브랜드가 헤드앤숄더"라는 진술은 내용상 성립하지 않는다. 화제가 된 키워드를 끼워 넣어 유입을 끌고 본문은 헤드앤숄더 제품을 소개하는 **홍보성 템플릿 글**로 판단된다. 즉 비교 후기가 아니다. 그런데 두 문서 모두 `signal_type = 이탈위험`으로 분류되어 있고, 그중 하나는 "헤드앤숄더 샴푸를 쓰고 나서 훨씬 개운해졌어요"로 끝나는 명백한 긍정 글이다.

### 5.2 이탈 신호 구성 확인

경쟁사 언급 문서(101건)의 `churn_signals` 구성 상위:

| churn_signals | n |
|---|---|
| `['안티트로']` | 31 |
| `['니조랄']` | 31 |
| `['가려움', '안티트로']` | 7 |
| `['트러블', '가려움', '안티트로']` | 5 |
| (이하 생략) | |

**경쟁사 브랜드명이 이탈 키워드로 등록되어 있다.** 62건은 다른 이탈 표현 없이 브랜드명이 등장했다는 이유만으로 이탈 신호가 잡혔다.

### 5.3 정량화

| | 경쟁사 언급 | 비언급 |
|---|---|---|
| 전체 | 101 | 1,643 |
| 이탈로 분류 | 83 (82.2%) | 335 (20.4%) |
| 이탈 분류 중 브랜드명 외 근거 없음 | 44 | 0 |
| 브랜드명 제외, 이탈 신호 1개 이상 | 39 (38.6%) | 507 (30.9%) |

- Active Switcher 세그먼트(83건, 이탈률 1.0, 경쟁사 언급률 1.0)는 "경쟁사 언급이면서 이탈로 분류된 문서" 집합과 동일하다. 그중 44건(53%)은 브랜드명 외의 이탈 근거가 없다.
- 공정한 비교를 위해 브랜드명을 제외한 "이탈 신호 출현율"로 맞추면 38.6% vs 30.9%다. 두 비율 차이의 z ≈ 1.6, p ≈ 0.1로, 경쟁사 언급 101건 표본에서는 유의한 차이라고 말하기 어렵다.
- 4월의 "4 대 1 격차"는 약 1.25 대 1로 줄며, 그마저 유의하지 않다.
- 주의: 브랜드명을 뺀 나머지 신호도 키워드 매칭이므로 38.6%와 30.9%는 정밀값이 아니라 순환을 걷어낸 대략값이다.

### 5.4 해석

헤드앤숄더 관련 검색으로 수집한 글에서 경쟁사가 언급되는 것을 "전환 고려 신호"로 정의한 것 자체는 하나의 설계 선택으로 방어할 수 있다. 문제는 **정의의 결과를 발견처럼 제시한 것**이다. 정의와 발견이 같은 것을 측정하면 그 숫자는 아무것도 증명하지 않는다.

같은 패턴이 하나 더 있을 수 있다. 원본 분석의 로지스틱 회귀 정확도 0.930은, 세그먼트가 이탈·경쟁사 플래그로 규칙에 따라 정의되고 그 플래그가 다시 입력 변수로 쓰였다면 규칙을 재현한 결과라 높을 수밖에 없다. 원본 코드의 입력 변수 목록을 확인하기 전까지는 가설이다.

### 5.5 데이터 품질 정리

- VoC는 검색 결과 발췌문(중앙값 약 140자)
- 유튜브 댓글 중복(4월 확인), 카페 템플릿형 홍보글(이번 확인)
- 키워드 기반 탐지기가 긍정 글을 이탈위험으로 오분류하는 사례 확인
- 평가셋 정리 시 "VoC와 무관하다"며 제외한 스팸 판별 질문은, 실제 데이터에 홍보성 글이 섞여 있었으므로 다시 볼 필요가 있다

## 7. 결정과 조치

### 7.1 결정

- **B(지금)**: 데이터는 그대로 두고, 82.2%에 기반한 주장을 README·포트폴리오·평가셋에서 바로잡는다. 에이전트에는 이 정의를 데이터 해석 규칙으로 전달해 단독 사실처럼 말하지 않게 한다.
- **A(계획)**: 상위 파이프라인에서 브랜드명을 이탈 키워드에서 분리하고 경쟁사 언급을 별도 축으로 두며, 홍보성 템플릿 글과 중복을 거른 뒤 신호 탐지 → 세그먼트 → 회귀를 재실행한다. 결과를 에이전트 DB에 재적재하고 인덱스와 배포를 갱신한다.

B를 먼저 하는 이유: 틀린 주장이 포트폴리오에 걸려 있는 상태가 가장 위험하며 B로 당일 해소된다. A는 키워드 사전, 세그먼트 정의, 회귀 설계를 다시 정하는 일이라 결정할 것이 많고, 서두르면 다른 측정 문제를 만들 수 있다.

### 7.2 에이전트 수정 (재빌드 1회로 묶음)

1. VoC 경로에 전체 개요 SQL 추가(총 문서 수, 소스별 분포, 경쟁사 언급 수) — 표본으로 전체를 단정하는 오류의 직접 대응
2. Reporter 규칙: VoC는 "1,744개 발췌문 중 유사도 상위 5건"임을 명시, 표본만으로 전체의 유무를 단정하지 않음, 확인형 질문은 전제를 데이터로 검증, 브랜드명 표기, 제목(`#`) 미사용, 82.2%의 정의적 성격 안내

## 8. 교훈

1. 각 부품이 정상이어도 경계에서 깨진다. 잘 동작하는 검색과 잘 동작하는 생성이 합쳐지면 닫힌 세계 단정이 나오고, 단발 API와 채팅 화면이 만나면 기억의 착시가 생긴다.
2. 측정하기 쉬운 지표는 그 지표가 보지 못하는 실패를 숨긴다. 이번에 발견된 문제는 전부 라우팅이 맞은 상태에서 일어났으므로 83.1%를 전혀 깎지 않았다.
3. 결과를 보고 정답을 바꾸면 안 된다. 라벨 재정의가 필요하면 그 사실을 기록하고 전후 수치를 분리해 보고한다.
4. 정의와 발견을 분리한다. "경쟁사 언급 = 이탈 신호"로 정의했다면 "경쟁사 언급 문서의 이탈률이 높다"는 발견이 될 수 없다.
5. 고치기 전에 가설을 검증한다. 쿼리 세 개로 가설 두 개가 기각되었고 효과 없는 작업을 피했다.
6. 바꾸면 다시 잰다. 모델, 화면, 데이터 중 하나라도 바뀌면 평가를 다시 돌린다.
7. 실제 사용자처럼 써 본다. 10분의 탐색적 사용이 몇 주의 정형 평가보다 많은 것을 찾아냈다.
8. 유창한 답변일수록 검증한다. Claude는 Llama보다 매끄러워서 틀린 단정도 설득력 있게 들린다.

       SUM(CASE WHEN signal_type = '이탈위험' THEN 1 ELSE 0 END) AS churn_labeled,
       SUM(CASE WHEN signal_type = '이탈위험'
                 AND regexp_replace(churn_signals, '''(안티트로|니조랄)''|[\[\],[:space:]]', '', 'g') = ''

       SUM(CASE WHEN regexp_replace(churn_signals, '''(안티트로|니조랄)''|[\[\],[:space:]]', '', 'g') <> ''
                THEN 1 ELSE 0 END) AS has_other_churn_signal
FROM voc_documents GROUP BY competitor_mentioned;
